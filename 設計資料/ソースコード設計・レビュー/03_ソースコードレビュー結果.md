## 3. 観点別の詳細

### 3.1 パフォーマンス（PF）

#### PF-01 起動時のデータ読込 ― 指摘（低）
- **該当**: `js/main.js:50-59`
- **内容**: 8 ファイルは `Promise.all` で並列取得しているが、その後の `transitions.json` / `audio.json` / `credits.json` は `await` を 3 回連続で行っており、直列に 3 往復している。モバイル回線（RTT 100〜300ms）では起動が 0.3〜1 秒程度余計にかかる。
- **推奨**: 11 ファイルすべてを 1 回の `Promise.all` にまとめる。

#### PF-02 描画コスト ― 指摘（低）
- **該当**: `js/ui/Renderer.js:91, 150`（`root.innerHTML = ""` → 背景 `<img>` を毎回生成）、各ギミックの `draw()`（数字 1 つ押すごとにギミック画像の `<img>` を作り直す：`NumericCodeGimmick.js:55-62, 110-127` ほか）
- **内容**: 所持品タップ・フラグ切替・メッセージ送り等のたびに背景画像を含む画面全体を作り直している。画像はキャッシュされるため通信は発生しないが、低スペック端末では再デコードによる一瞬のちらつき・レイアウトのガタつきが起きる可能性がある。
- **評価**: 設計意図（2.4 単純さ優先）として妥当な判断であり、現状規模で致命的ではない。本番画像に差し替えた段階で実機確認を推奨。
- **推奨**: 問題が見えた場合、背景・ギミック画像要素だけを保持して再利用する（src が同じなら作り直さない）。

#### PF-03 不要なネットワーク要求 ― 指摘（低）
- **該当**: `data/views.json:26,37,48,…`（`assets/note/note_*.webp`）、`js/ui/Renderer.js:265-271`
- **内容**: `assets/note/` フォルダが存在しないため、ノートを表示するたび（ページ送り・メッセージ送りの再描画ごと）に 404 の画像要求が発生し、`onerror` でプレースホルダーに切り替わる。404 は通常キャッシュされないため毎回通信する。
- **推奨**: 素材が揃うまでの暫定問題なので、素材配置で解消する。恒久策としては、一度失敗したパスを記憶して再要求しない仕組み（失敗パスの Set）を検討。

#### PF-04 音声の生成・先読み ― 指摘（低）
- **該当**: `js/audio/AudioManager.js:104`
- **内容**: SE 再生のたびに `new Audio(file)` を生成しており、先読み（preload）も無い。各 SE の初回再生時にファイル取得が発生し、モバイルではタップから音が鳴るまでに遅延が出る可能性がある。
- **推奨**: 初回ユーザー操作時に SE を先読みしておく、または Web Audio API（AudioBuffer）で読み込み済みの音を再生する方式を検討。

#### PF-05 素材サイズ ― 要検討（低）
- **該当**: `assets/bgm/`（合計約 16MB。`BGM_tie no wa.mp3` 5.1MB、`BGM_The Dark Eternal Night.mp3` 3.4MB 等）
- **内容**: 背景画像は WebP で 1 枚 100KB 前後と適切。BGM は再生時にストリーミングされるため起動時の負担にはならないが、通しプレイで全曲を聞くと十数 MB の通信になる。
- **推奨**: ループ BGM であれば 96〜128kbps 程度への再エンコードで半分以下にできる。音質との兼ね合いで判断。

#### PF-06 メモリリーク ― OK
- 画面の再構築で古い DOM ごとリスナーが破棄される設計。`MutationObserver` はモーダルが外れた時点で `disconnect`（`main.js:727-732`）、早送りの `setInterval` は確実に `clearInterval`、自動再生解除のリスナーは `once:true`。ログは 200 件上限（`main.js:931-935`）。リークの要因は見当たらない。

#### PF-07 保存処理の頻度 ― OK

#### PF-08 本番不要処理 ― 指摘（低）
- **該当**: `js/ui/Renderer.js:212-220`（背景タップ座標を `console.log`）、`AudioManager.js:97, 113`（未設定音声のログ）

#### PF-09 計算量 ― OK

### 3.4 堅牢性（RB）

#### RB-01 データの誤記検出 ― 指摘（中）
- **該当**: `js/engine/ConditionEval.js:11-73`
- **内容**: 次の 3 つのケースで、データの書き間違いが **エラーにならず「条件成立」として扱われる**。Node で `evaluate` を直接呼び出して確認した。

| ケース | 例 | 期待 | 実際 |
|---|---|---|---|
| 未知のキー（綴り誤り） | `{ "hasitem": "x" }` | エラー or 偽 | **真** |
| 範囲の複合指定 | `{ "playPart": { "gte": 2, "lte": 5 } }`（パート 7） | 偽 | **真**（最初の `gte` しか見ない） |
| allOf と他キーの併記 | `{ "playPart": 1, "allOf": [{}] }`（パート 7） | 偽 | **真**（`allOf` 以外を無視） |

- ルールは先頭一致のため、誤記したルールが常に成立して後続のルールを隠してしまう。現行データにはこの誤記は無い（テスト D-01・X-01 は参照先の存在は確認するが、条件キーの綴りは確認していない）。
- **推奨**: `evaluate` で既知キー以外があれば `console.error` を出す、`evalNumberCond` を全キーの AND にする、`allOf`/`anyOf` と他キーを併記した場合も両方評価する。あるいは `rules.test.mjs` に「全 when の全キーが既知のキーか」を検査するテストを追加する。

#### RB-02 想定外データ型 ― 指摘（低）
- `resolveMessage`（`RuleResolver.js:37-50`）に配列でもない文字列でもないオブジェクト（例 `{ "text": "x" }`）を渡すと `TypeError: messageDef is not iterable` で停止する（Node で確認）。`items.json` の `description` / `placeholder`、`playParts.json` の `notYetMessage` で書式を誤ると、アイテム拡大やカメラタップで例外になる。
- `resolveGimmickResult`（`ActionExec.js:242-245`）は `gimmick` が見つからない場合の確認が無い（現状は呼び出し元で存在確認済みのため発生しない）。
- `advanceToPlayPart`（`ActionExec.js:221-226`）で存在しないパートに進んだ場合、`phase:"play"` のまま保存され、次回起動時に `normalizeLoadedState` でセーブごと破棄される（データ誤りが前提）。
- **推奨**: `resolveMessage` の末尾で配列以外を弾く。データ検証テストに書式チェックを追加。

#### RB-03 全体の例外処理 ― 指摘（中）
- **該当**: `js/main.js:1151`（`main();` の戻り値の Promise を処理していない）、`window.onerror` / `unhandledrejection` の登録なし
- **内容**: データ読込の失敗は丁寧に処理されているが、読込後の描画・ルール実行で想定外の例外（RB-02 のようなデータ誤り、ブラウザ固有の不具合）が起きると、コンソールにだけ出て画面が固まる／真っ白になる。スマホの利用者はコンソールを見られないため、原因も対処も分からない。
- **推奨**: `window.addEventListener("error")` と `"unhandledrejection"` で「問題が発生しました。再読み込みしてください」と再読み込みボタンを出す。セーブは操作単位で保存済みのため、再読み込みで復帰できる。

#### RB-04 状態管理の複雑さ ― 指摘（中）
- **該当**: `main.js:131-160` ほか
- **内容**:
  1. 入力の可否が `startMessagesPending` / `pendingAutoClear` / `tapGuardUntil` / `currentModalStatusEl` / `currentModalOverlay` / `msgQueue` の状態 / `zoomShownItemId` の組合せで決まり、判定がルートのキャプチャ処理（`main.js:1070-1108`）と各ハンドラ冒頭の `if (msgQueue.isBusy() || pendingAutoClear) return;`（5 か所）に分散している。これまでの修正経緯（コメント多数）からも、この部分が不具合の温床になっていることがうかがえる。現状はブラウザテスト E-09〜E-23 で担保されている。
  2. **リセット漏れ（軽微な不具合）**: エンディングの「タイトルへ戻る」（`main.js:1041-1046`）と `startGame`（`main.js:989-997`）では `faceCycleIndex`（表情タップのループ位置、`main.js:142`）がリセットされない。同じタブで 2 周目を遊ぶと、パート 3〜7 の表情タップが 1 行目からではなく前回の続きから始まる（リロードすれば 0 に戻るため、リロード有無で挙動が変わる）。デバッグジャンプ（`jumpToPlayPart` 等）でも同様。

### 3.5 安全性（SF）

#### SF-01 デバッグ機能のリリース混入 ― 指摘（高）

## 4. 良い点（維持を推奨する設計）

1. **データ駆動の徹底**：分岐・文言・素材が JSON にあり、JS はアイテム名やスポット名を一切知らない。仕様変更の大半が JSON 編集で済む。
2. **ロジックと描画の分離**：Engine が DOM を知らないため、ブラウザなしで全分岐を検証するテストが成立している。
3. **安全な DOM 構築**：`textContent` のみで文字列を扱い、XSS の経路が無い。
4. **壊れても止まらない設計**：画像欠落・セーブ破損・localStorage 不可・通信タイムアウト・多重タブに個別の対策がある。
5. **経緯の残るコメント**：なぜその処理が必要かが、発生した不具合とともに記録されている。
6. **充実したテスト**：総当たり・乱択・異常系（遅延・404・改ざん・連打・長時間）まで網羅し、ポート番号を埋め込まない運用も守られている。
